# RCA — iqfoam-business redeploy failed at health_check (run 5a5cec64-934a-490e-bc41-2079e6af62fb)

## Symptom
Redeploy failed at the `health_check` step: `backend unhealthy at /health: status 503` after 3 attempts. Pod events show the startup probe getting `connection refused` on `http://<pod>:8080/` — nginx/backend never came up, so the pod never became ready and was killed.

## Root cause (confirmed)
The FastAPI backend crashes during startup (`lifespan` / `on_startup` → `initialize_multi_company()` at `/app/backend/server.py:17738`) while creating a MongoDB index.

The new code requests:
`{ v: 2, unique: true, key: { invoice_id: 1 }, name: "invoice_share_once" }`

But the production DB (`iqfoam-business-test_database`, collection `invoice_share_links`) already has an index with the **same name but a different key spec**:
`{ company_id: 1, invoice_id: 1 }, name: "invoice_share_once", unique: true`

MongoDB rejects this with `OperationFailure code 86 IndexKeySpecsConflict` ("An existing index has the same name as the requested index"). The exception propagates out of the startup lifespan, uvicorn logs `Application startup failed. Exiting.` / `Backend failed to start at initialization, exiting`, the container dies, nginx refuses on :8080, and health_check returns 503.

### Evidence
- `mongo_query list_indexes` on `invoice_share_links` → existing index: `{"key":{"company_id":1,"invoice_id":1},"name":"invoice_share_once","unique":true}`. The code wants key `{invoice_id:1}` under the same name.
- `get_pod_events` (run 5a5cec64): `Startup probe failed: ... :8080 connect: connection refused`, then `Killing` both pods.
- Identical traceback captured verbatim in the three prior failed runs (4de047d5, 782f4555, rollbacks), all pointing at `server.py:17738 initialize_multi_company` → `base_db.invoice_share_links.create_index(...)` → `IndexKeySpecsConflict`.

### Secondary (non-fatal) note
The same startup also logs `WARNING:root:Index on prices not created: ... E11000 duplicate key ... zone_1_category_1_size_1 dup key {zone:1, category:"Ribbon Black", size:"1070x100"}`. This one is caught/warned (not fatal). Note the live `prices` collection now carries a compound unique index `company_id_1_zone_1_category_1_size_1`, so the old `zone_1_category_1_size_1` unique index referenced in the warning no longer exists — this is not what blocks the deploy, but there IS duplicate data (zone/category/size `Ribbon Black / 1070x100`) that would break any attempt to recreate a `{zone,category,size}`-only unique index.

## Fix (Code — E1)
In `initialize_multi_company()` make the `invoice_share_once` index creation reconcile a pre-existing index with a different key, e.g. before `create_index(...)`:
- Look up the existing index named `invoice_share_once`; if its key spec differs from the desired `{ invoice_id: 1 }`, `drop_index("invoice_share_once")` then recreate it — OR give the new index a distinct name — OR wrap the create_index in a try/except that drops-and-retries on `OperationFailure` code 86.
- Also guard against `E11000`: the new unique index on `{ invoice_id: 1 }` will fail if `invoice_share_links` contains multiple docs with the same `invoice_id` across companies. Verify/dedupe data, or keep the key company-scoped.

Startup DB-index setup should be idempotent and must not let a single `create_index` exception kill the whole app boot.

## Alternative unblock (DB — optional, riskier)
A one-time drop of the stale `invoice_share_once` index on `invoice_share_links` via DB Manager would let the new code recreate it — but only if data has no duplicate `invoice_id`s; otherwise the recreate hits E11000. The code fix above is the durable solution.

## Why not auto-recovered
This is a deterministic source-level startup crash tied to existing production index state; it is not a manifest, tier, or secret issue. Re-firing the pipeline with the same image + DB state reproduces the same crash. Needs the code fix above, then redeploy.
